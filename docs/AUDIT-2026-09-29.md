# GRIM audit findings — 2026-09-29

External review of GRIM 0.6.3 (npm `grim-mcp`) performed while building
[VulnScope](https://github.com/AbduljabbarBXR/vulnscope), an audit platform
that uses GRIM as its code/deps/secrets engine. All findings are
reproducible from the commands below.

**Correction to an earlier, inaccurate report:** an initial review claimed the
malware engine missed a textbook PHP webshell entirely. That was wrong — GRIM
*does* detect webshells when they sit in a recognized web directory. The real
gap is narrower and is described in **Finding 1**. Recording this so nobody
wastes time on the wrong bug.

---

## Finding 1 — flat-layout applications get no web exposure coverage

**Severity: High**
**Component:** `src/grim/engines/exposure.py`, `_in_web_path()`

Web-path rules gate on path *segments*. A file is only audited as
web-served when some parent directory is named `public`, `public_html`,
`www`, `htdocs`, `web`, `static`, `assets`, `uploads`, `upload`, `files`,
`storage`, `img`, `images` or `media` (`WEB_SEGMENTS`).

Consequently a **flat-layout application** — PHP or server files sitting at
the repository root with no conventional web subdirectory — is never treated
as web-served. The `malware` command also surfaces no coverage for these
files, since its exposure rules share the same gate.

This is the most common legacy layout in the wild: entire generations of PHP
apps are exactly `index.php`, `config.php`, `shell.php` at the root.

### Repro

```bash
mkdir flat && cd flat
printf '<?php system($_GET["c"]); ?>' > index.php
printf 'const AWS_KEY = "AKIAIOSFODNN7EXAMPLE";' > config.php
# no package.json, no public/, no www/

grim malware .        # -> Total findings: 0
grim scan .           # -> secrets rule fires (AWS key), web exposure: nothing
grim tool detect_stack --path .
#   "stacks": [], "web_dirs": []   <- the root is never a web dir
```

Compare with the same file inside `web/`:

```bash
mkdir web && cp index.php web/
grim malware .        # -> 5 CRITICAL, incl. "Executable php file in web-served directory"
```

### Suggested fix

Treat the scan root itself as a web-served directory when the detected stack
is a web framework (express detected from `package.json`, PHP detected from
`.php` files, Laravel/Django per the manifest). Concretely, have
`detect_stack()` append the root to `web_dirs` when a web stack is present,
and relax `_in_web_path()` to accept the root-relative top level in the same
case.

Fallback while shippable today: when a `.php` file exists anywhere and no
web dir was detected, treat the containing directory as web-served.

### Mitigation for VulnScope users

In the platform, run audits against the deployed directory layout (the one
that contains `public/`) rather than a raw dump of the repo. This matches
reality anyway, since exposure rules only mean something against what the
server actually serves.

## Finding 2 — `grim tool` rejects positional paths, contradicting its own docs

**Severity: Low (documentation/CLI ergonomics)**
**Component:** `src/grim/tools.py` — `tool` subcommand

The `list` output describes tools such as `detect_stack` as
"Identify the project stack(s) and web-served directories. Run this first."
MCP-consumed tools take a `path` parameter, which invites the obvious CLI
form:

```bash
grim tool detect_stack /path/to/app
# grim: error: unrecognized arguments: /path/to/app
```

The path must be passed as a flag instead:

```bash
grim tool detect_stack --path /path/to/app   # works
```

`grim tool --help` does show the `--path` option, so this is a discoverability
and convention issue rather than a broken feature — but the subcommand is the
one most likely to be tried first by a new user scripting a single-tool run,
and it silently fails in the shape they will naturally type.

### Suggested fix

Accept an optional positional after the tool name that maps to `--path`, or
have `list` print the exact invocation form for each tool.

## Verified working (no action needed)

Recorded so the coverage picture stays honest and so these are not
"regressed" in a future refactor:

- SAST correctly flags `<?php system($_GET['c']); ?>` as **CRITICAL**
  "Command execution fed by request input" with CWE-94, ATT&CK T1059.
- Secret detection catches AWS access keys, with a masked-evidence line
  (`AKIA…LE(len=20)`) that is safe to paste into reports.
- SBOM emits valid CycloneDX 1.5 with a well-formed UUID serial.
- Endpoint inventory parses Express routes with explicit line references.
- `scan` produces ranked, deduplicated JSON with stable finding IDs —
  usable directly as an engine feeding a reporting layer.
